Retrying an action without duplicating it

November 10, 2026

Note by Armel Tenkiang.

On this page
  1. Uncertainty arrives after sending
  2. Keep the identity
  3. Duplicates are not conflicts
  4. Scope of this note

In Home, a lost response must not turn a second attempt into a second change.

Uncertainty arrives after sending

A device sends an action and loses its connection before receiving an acknowledgement. It does not know whether the hub applied it. Retrying with a new identity would hide that uncertainty and could produce a second change.

Keep the identity

The client records the operation in a persistent queue before sending it. Subsequent attempts retain its identity. The hub can then distinguish a new action from one already applied, rather than treating every message as a new intention.

This does not make the network reliable. It makes the same operation recognizable despite uncertain delivery. An acknowledgement needs to describe the outcome, not merely the arrival of a message.

Duplicates are not conflicts

An already-applied action and an action based on an outdated revision require different responses. In the latter case the client needs to show the conflict; assigning another identity or overwriting the record does not resolve it.

Scope of this note

This note describes the 27 October 2026 Home source snapshot and previously recorded test/build evidence. It does not claim physical-TV acceptance or public release.
