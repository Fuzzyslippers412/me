Réessayer une action sans la dupliquer

10 novembre 2026

Note de Armel Tenkiang.

Sur cette page
  1. L’incertitude survient après l’envoi
  2. Conserver l’identité
  3. Un doublon n’est pas un conflit
  4. Portée de cette note

Dans Home, une réponse perdue ne doit pas transformer une nouvelle tentative en une seconde modification.

L’incertitude survient après l’envoi

Un appareil envoie une action et perd la connexion avant de recevoir la confirmation. Il ignore si le hub l’a appliquée. Réessayer avec un nouvel identifiant masquerait cette incertitude et pourrait produire une seconde modification.

Conserver l’identité

Le client enregistre l’opération dans une file persistante avant l’envoi. Les tentatives suivantes conservent son identifiant. Le hub peut ainsi distinguer une action nouvelle d’une action déjà appliquée, sans considérer chaque message comme une nouvelle intention.

Cela ne rend pas le réseau fiable. Cela rend la même opération reconnaissable malgré une livraison incertaine. La confirmation doit décrire le résultat, pas seulement l’arrivée d’un message.

Un doublon n’est pas un conflit

Une action déjà appliquée et une action fondée sur une révision dépassée exigent des réponses différentes. Dans le second cas, le client doit montrer le conflit ; changer l’identifiant ou écraser le registre ne le résout pas.

Portée de cette note

Cette note décrit le code de Home du 27 octobre 2026 et les résultats de tests et de compilation déjà enregistrés. Elle ne revendique ni validation sur une télévision physique ni lancement public.
